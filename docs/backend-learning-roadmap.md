## 零、先建立整体认知

一个企业级后端不是几个 API，而是完整的业务系统。一次请求的生命周期：

```text
客户端
  ↓ HTTP 请求
路由层 Router        声明接口契约
  ↓
参数校验 Schema      挡住非法输入
  ↓
业务层 Service       业务规则的唯一归属地
  ↓
数据访问层 Repository 唯一能出现 SQL 的地方
  ↓
数据库 MySQL
```

横向贯穿所有层的关注点：

```text
认证与授权 / 异常处理 / 日志与监控 / 事务管理 / 缓存
异步任务 / 文件存储 / 测试 / 部署 / 安全 / 性能 / CI
```

学习每个知识点时，都把它放回这张图里理解——它属于哪一层，为什么属于那一层。

## 第一阶段：分层架构与请求生命周期（已完成第一轮）

目标：理解一个请求在系统中的完整旅程，以及每一层的职责边界。

需要掌握：

- Router / Schema / Model / Service / Repository 各自的职责
- 依赖注入（Dependency Injection）
- 配置管理
- 模块之间如何协作
- 为什么不能把所有代码都写在路由函数里

核心理念：

> 每一层只负责自己的事情。

判断分层有没有守住，看这几条硬性边界：

- `services/` 不 import fastapi —— 业务层不该知道 HTTP 的存在
- `services/` 不写 SQL —— 数据读写全部委托 `repositories/`
- `repositories/` 不做业务判断、不抛 HTTPException
- `api/` 不含业务逻辑，只做「接收 → 转交 → 装响应」

本项目已落地的目录结构：

```text
app/
├── main.py              应用入口、挂载中间件与异常处理器
├── config.py            Pydantic Settings 配置
├── db.py                Engine / Session 依赖
├── core/
│   ├── security.py      密码哈希（通用安全能力）
│   ├── exceptions.py    业务异常 + 各自对应的 HTTP 状态码
│   └── handlers.py      全局异常处理器
├── api/
│   ├── deps.py          鉴权依赖（HTTP 协议细节留在这里）
│   └── user.py 等       路由，只声明契约
├── schemas/             DTO：请求校验 + 响应白名单
├── models/              ORM 表定义
├── services/            业务规则
├── repositories/        数据访问，唯一能写 SQL 的地方
└── tests/               pytest + SQLite 内存库
```

第一轮重构的实际收益（user 模块）：

- `api/user.py` 从 117 行降到 61 行，`try/except` 归零
- 业务函数可被 CLI 脚本、定时任务、单元测试直接调用，不需要起 web 服务
- 10 条测试用例通过

## 第二阶段：认证与授权（下一步）

目标：区分「你是谁」和「你能做什么」。

### 认证 Authentication

回答：**你是谁？**

例如通过 JWT 判断当前请求属于哪个用户。本项目已实现：

- `services/auth.py` —— `create_access_token` / `decode_access_token`（纯逻辑）
- `api/deps.py` —— `get_current_user_id`（从请求头取 token，失败补 `WWW-Authenticate` 头）

### 授权 Authorization

回答：**你有权限做这件事吗？**

- 用户只能查看自己的任务
- 管理员可以查看所有用户
- 普通用户不能删除别人的数据

需要掌握：

- 登录流程、密码哈希
- JWT 结构、Access Token / Refresh Token
- Token 过期与撤销
- 角色权限模型（RBAC）
- 资源权限模型（谁拥有这条数据）

最常见的错误，也是本项目当前存在的真实问题：

> 只验证了「用户已登录」，没有验证「用户是否拥有当前资源」。

```text
GET /api/messages
```

现状：任何登录用户都能读到全部人的聊天记录。修法是给 `chat_messages`
加 `user_id` 外键，查询时按当前用户过滤。

```text
GET /tasks/100
```

不能只判断用户已登录，还要判断任务 100 是否属于当前用户。

必做的越权测试：

- 用户 A 能否通过改 `task_id` 读到用户 B 的数据？
- 用户 A 能否修改用户 B 的数据？
- 普通用户能否调用管理员接口？

很多真实安全事故不是复杂漏洞，而是资源权限校验缺失。

## 第三阶段：数据库与 ORM

目标：先会建模，再谈接口。

需要掌握：

- 表设计、主键、外键
- 一对一 / 一对多 / 多对多
- 索引、唯一约束、非空约束
- 软删除、时间字段
- 分页、排序、过滤
- SQL 事务
- ORM 的优点与边界
- N+1 查询问题

FastAPI 项目还需要：

- SQLAlchemy / SQLModel
- 数据库 Session 生命周期
- Alembic 数据库迁移
- 开发与生产的数据库配置隔离

关系设计示例：

```text
users 1 ──── N tasks
tasks 1 ──── N task_records
categories 1 ──── N tasks
```

核心理念：

> 业务数据应该如何建模，数据约束应该由谁保证。

具体例子：任务名称不能重复，是由代码 `if` 判断，还是由数据库唯一索引保证？

答案是后者优先。原因是竞态条件——两个并发请求同时执行「先查一下，
没有就插入」，两次查询都会说「不存在」，然后双双插入。企业项目通常
数据库层和代码层共同保证：数据库兜底正确性，代码层负责给出友好提示。

本项目 `services/user.py` 的注册逻辑就是这个模式的落地。

已知待办：`main.py` 启动时 `init_db()` 硬编码建表，应换成 Alembic 迁移。

## 第四阶段：异常处理与统一响应

目标：让错误行为统一、可理解、可排查。

需要掌握：

- HTTP 状态码语义
- 参数校验错误 / 业务异常 / 数据不存在 / 权限不足 / 重复数据 / 数据库异常
- 全局异常处理器
- 统一错误响应格式
- 错误日志与用户提示的区别

统一错误结构：

```json
{
  "code": 409,
  "message": "用户名已存在",
  "error": "USERNAME_TAKEN",
  "data": null
}
```

核心理念：

> 给用户看的错误信息，和给开发者看的错误日志，不应该相同。

用户不该看到 SQL、堆栈、内部路径；日志里必须保留足够的排查信息。
本项目 `core/handlers.py` 的两个处理器就是这条原则的实现：
业务异常用 `info` 记录不带堆栈，未预期异常用 `error` + `exc_info=True`
记录完整堆栈，但对外只返回一句通用文案。

## 第五阶段：业务建模与核心业务逻辑

目标：从「接口开发」进入「后端开发」。

以任务功能为例，需要先回答这些问题：

- 什么是任务？有哪些状态？
- 哪些状态可以互相转换？
- 已完成的任务是否允许编辑？
- 删除是物理删除还是软删除？
- 重复提交是否会产生重复任务？
- 截止时间如何处理时区？
- 用户注销后任务如何处理？
- 是否需要操作记录？

状态机设计：

```text
pending → in_progress → completed
   ↓           ↓            ↓
cancelled  cancelled     archived
```

「完成任务」的完整业务流程：

```text
1. 查询任务
2. 验证任务属于当前用户      ← 授权，别漏
3. 验证当前状态允许完成      ← 状态机约束
4. 更新任务状态
5. 记录完成时间
6. 写入操作记录
7. 提交事务
```

核心理念：

> 接口是业务能力的入口，Service 才是业务规则的核心。

业务规则要集中在 Service 层，不能散落在多个路由里——否则同一条规则
会有多份实现，改一处漏一处。

## 第六阶段：事务与数据一致性

目标：保证多个相关操作整体成功或整体失败。

需要掌握：

- 事务的提交与回滚
- ACID：原子性、一致性、隔离性、持久性
- 多表同时修改
- 事务边界应该放在哪一层
- 并发更新、乐观锁、悲观锁
- 幂等性

例子：完成任务时需要同时做三件事：

```text
1. 修改任务状态
2. 增加用户积分
3. 写入任务记录
```

不在同一事务里就可能出现：

- 任务显示已完成，但积分没加
- 积分加了，但任务记录没写
- 记录写了，但任务状态更新失败

关于事务边界，一条实用判断：

> 单个写操作可以在 Repository 里 commit；
> 一旦出现「多个写操作必须凑成一个整体」，commit 就要上提到 Service 层统一控制。

### 幂等性

> 同一个请求执行一次和执行多次，结果应该一致。

移动端网络不稳时，用户可能连续提交两次「完成任务」。后端不能因此
重复发积分或创建重复记录。常见做法是客户端传幂等键（idempotency key），
服务端据此去重。

## 第七阶段：API 设计规范

目标：把 API 当作长期契约来设计。

需要掌握：

- URL 资源命名、HTTP 方法、状态码
- 分页、筛选、排序、搜索
- 版本控制
- 请求幂等性
- API 文档
- 向后兼容

资源命名：

```text
GET    /api/v1/tasks
POST   /api/v1/tasks
GET    /api/v1/tasks/{task_id}
PATCH  /api/v1/tasks/{task_id}
DELETE /api/v1/tasks/{task_id}
```

分页统一格式：

```text
GET /api/v1/tasks?page=1&page_size=20
```

```json
{
  "items": [],
  "total": 100,
  "page": 1,
  "page_size": 20
}
```

核心理念：

> API 是前后端之间的长期契约，不是临时写给自己调用的函数。

一个具体的安全实践：响应模型用白名单 DTO，不要直接返回 ORM 表模型。

```text
不好：return user                              表里加字段就自动泄露
凑合：return user.model_dump(exclude={...})     忘写 exclude 就泄露
推荐：return UserPublic.model_validate(user)    只有声明的字段才会出去
```

本项目 `schemas/user.py` 的 `UserPublic` 就是这个模式。
已知待办：`jobs.py` / `careers.py` / `industries.py` 等只读接口
仍直接把 SQLModel 表模型当响应模型。

## 第八阶段：测试

目标：不再依赖手动开 Swagger 点接口。

需要掌握：

- 单元测试 / 集成测试 / API 测试

- 权限测试、异常场景测试

- 覆盖率、回归测试

技术栈：

```text
pytest
httpx
pytest-asyncio  （测异步代码时需要）
```

优先覆盖的场景：

**用户相关**

- 注册成功 / 重复注册 / 密码太短
- 登录成功 / 密码错误
- 未登录访问 / Token 过期 / Token 无效

**任务相关**

- 创建、查询、修改、删除
- 查询别人的任务（越权，必须失败）
- 非法状态转换

**数据相关**

- 事务回滚
- 唯一约束冲突
- 分页边界
- 空结果

本项目的做法：SQLite 内存库 + `app.dependency_overrides` 替换

核心理念：

> 测试的价值不是证明代码「现在看起来没问题」，
> 而是保证以后改代码时不会破坏已有行为。

## 第九阶段：日志、配置与可观测性

目标：线上出问题时能知道发生了什么。

需要掌握：

- 分级日志：`DEBUG` / `INFO` / `WARNING` / `ERROR`
- 请求日志、异常堆栈、请求 ID
- 用户操作日志
- 环境变量、多环境配置隔离
- 健康检查接口
- 指标监控、慢请求排查

三个概念要分清：

```text
日志 Logging   系统发生了什么
指标 Metrics   系统运行得怎么样
追踪 Tracing   一次请求经过了哪些模块
```

最基础的要求：

```text
GET /api/health
```

用于判断服务是否启动、数据库是否可连、关键依赖是否正常。
本项目已有这个接口，但目前只返回固定的 `{"status": "ok"}`，
没有真正探测数据库连通性——这是可以改进的地方。

配置安全：密码、JWT 密钥、数据库连接串绝不硬编码。本项目已经在用
环境变量 + `pydantic-settings`，方向正确。`services/auth.py` 的
`_require_secret()` 是一个值得记住的模式：没配密钥就直接 503 拒绝服务
（fail closed），绝不回退到默认密钥——那等于把签名密钥公开在代码里。

## 第十阶段：安全开发

目标：安全是默认设计，不是上线前补救。

需要掌握：

- 密码哈希、JWT 密钥保护
- CORS
- SQL 注入、XSS、CSRF
- 请求频率限制（限流）
- 文件上传安全
- 输入长度限制
- 敏感信息脱敏
- 权限越权
- 暴力破解防护
- 生产环境关闭调试信息与 API 文档
- 数据库不直接暴露公网

本项目已做到的：

- 密码只存 bcrypt 哈希
- JWT 密钥缺失时 fail closed
- 生产环境关闭 `/docs`、`/redoc`、`/openapi.json`
- 登录失败不区分「用户不存在」和「密码错误」，防用户名枚举
- 管理接口用独立 API Key，且用 `secrets.compare_digest` 做常量时间比较

还缺的：登录接口没有限流（可被暴力破解）、`/api/messages` 存在越权。

核心理念：

> 不能依赖调用方「按规矩使用」。所有输入都是不可信的。

## 现阶段最该内化的核心理念

1. **分层思想** — 不同代码放在合适的层
2. **单一职责** — 一个模块只负责一类事情
3. **依赖注入** — 让组件可替换、可测试、可复用
4. **数据建模优先** — 先理解业务实体和关系，再设计接口
5. **事务一致性** — 相关操作整体成功或整体失败
6. **认证与授权分离** — 登录 ≠ 拥有所有权限
7. **错误可控** — 统一返回、必被记录、可追踪
8. **接口契约** — API 要稳定、清晰、可演进
9. **幂等性** — 重复请求不产生错误的重复结果
10. **可观测性** — 线上系统必须能知道发生了什么
11. **安全默认开启** — 不依赖调用方「正常使用」
12. **可维护性优先** — 代码不仅要能跑，还要方便改和排查

## 每个主题的学习流程

```text
1. 先理解概念
2. 找出本项目中对应的问题
3. 设计简单方案
4. 修改代码
5. 编写或补充测试
6. 运行验证
7. 提炼知识点总结，写入 docs/notes/
```

第 7 步不能省，且是硬性要求。能讲清「为什么这样设计」，才算真的掌握了。

知识点总结按固定五段组织，便于记忆和面试复习：

```text
一句话总结  →  面试开场答法
```
