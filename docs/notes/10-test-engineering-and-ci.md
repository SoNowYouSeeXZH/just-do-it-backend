# 10 自动化测试工程化与 CI 门禁

> 对应迭代 5 · 已完成

## 一句话总结

自动化测试的价值不是“本地跑过一次”，而是让每次提交都自动验证核心功能、权限、异常和架构边界，并用覆盖率门禁尽早发现未测试代码。覆盖率是风险信号，不是盲目追求的数字；关键业务分支比单纯的百分比更重要。

## 核心概念

### 测试金字塔

```text
单元测试       单个函数，无外部依赖       快、数量多
集成测试       多层协作 + 测试数据库      验证真实协作
API 测试       完整 HTTP 请求/响应        验证对外契约
E2E 测试       前后端完整链路             慢、只覆盖关键路径
```

实际工程通常以集成测试和 API 测试为主：HTTP 请求经过 Router、Schema、Service、Repository，再进入 SQLite 内存库。数据库没有 mock，只把真实数据库实现替换成轻量数据库；第三方大模型网络调用则用 monkeypatch 替换，因为它慢、收费且结果不稳定。

### 测试隔离

每个测试函数使用一套独立 SQLite 内存库；`dependency_overrides` 和 monkeypatch 在用完后清理。测试不依赖执行顺序，单独运行和整套运行结果一致。

测试隔离不只是数据库数据隔离，还包括：

```text
全局配置
FastAPI 依赖覆盖
外部服务 mock
环境变量
时间 / 随机数（必要时固定）
```

### 覆盖率

覆盖率回答的是：代码执行过多少；它不能回答：断言是否有价值、边界是否正确、并发是否安全。

因此可以使用：

```text
pytest-cov 统计覆盖率
--cov-fail-under=80 设置最低门槛
.coveragerc 排除一次性脚本等不属于请求路径的代码
```

覆盖率数字只能作为风险信号，仍要重点检查网络异常等关键分支。门槛设为 80% 是底线，不代表 80% 就足够。

### 架构测试

普通测试验证“结果对不对”，架构测试验证“代码组织有没有被破坏”：

```text
services 不依赖 fastapi
services 不直接构造 SQL
api 不直接查询数据库
repositories 不依赖业务异常
schemas 不依赖 ORM / Service
```

使用 Python `ast` 解析 import，而不是 grep 文本，避免把注释中的字符串误判成真实依赖。

### CI 门禁

本地测试只能保证开发者当前环境。CI 使用干净环境重新安装依赖并执行测试：

```text
提交 / Pull Request
  ↓
安装 requirements.txt + requirements-dev.txt
  ↓
运行 pytest
  ↓
测试失败或覆盖率低于 80%
  ↓
禁止合入
```

这把“必须测试”从团队约定变成自动化规则。

## 面试高频问答

**Q：单元测试、集成测试、E2E 测试怎么选择？**

单元测试验证单个函数的纯逻辑，速度最快；集成测试验证多个模块与数据库协作；E2E 测试验证用户完整链路，成本最高。核心业务规则用单元测试覆盖，关键接口用集成/API 测试覆盖，E2E 只保留最重要的用户路径。不能只选一种。

**Q：为什么不 mock 数据库？**

mock 会让测试通过却无法证明真实 SQL、唯一约束、事务和字段映射正确。这种方案使用 SQLite 内存库执行真实数据库操作，保留了 SQL 执行和约束验证；MySQL 特有语法、索引和锁行为则需要在 CI 中用真实 MySQL 验证。

**Q：覆盖率达到 100% 是否代表代码质量好？**

不代表。覆盖率只说明代码行被执行过，不能说明断言正确、异常处理合理或并发安全。应优先覆盖核心业务路径、权限分支、事务回滚和边界值。覆盖率更适合作为“未测试风险的预警指标”和最低门槛。

**Q：为什么测试在本地通过，CI 还可能失败？**

环境差异：Python/依赖版本不同、环境变量缺失、时区不同、数据库方言不同、测试依赖本地 Docker 或已有数据。CI 用干净环境和锁定版本重跑，能暴露这些隐式依赖。测试本身也必须隔离，不能依赖本地 `.env` 或测试执行顺序。

**Q：测试发现了一个失败，应该改测试还是改代码？**

先判断失败是否反映真实契约。若代码行为错误，改代码；若需求变了，更新测试和契约；若测试依赖环境或执行顺序，修测试隔离。不能为了绿色随意放宽断言，否则测试会失去保护作用。

**Q：CI 为什么要把测试作为合入门禁？**

因为人工 review 很难覆盖所有回归场景，而且测试只在本地执行无法保证提交内容和本地环境一致。CI 在干净环境自动执行，测试失败或覆盖率低于底线就阻止合入，把质量要求前置到交付流程中。

## 易错点

- **只测正常路径。** 权限、异常、边界和回滚分支更容易出真实 bug。
- **mock 数据库。** 失去对真实 SQL、约束和事务的验证。
- **覆盖率越高越好。** 没有有效断言的代码执行不等于被正确测试。
- **测试依赖本地 `.env`。** CI 没有相同环境，结果会不稳定；测试必须显式设置需要的配置。
- **测试之间共享数据。** 单独运行能过、整套运行失败，通常是隔离问题。
- **忽略架构测试。** 业务测试可能全绿，但 Service 已经偷偷写 SQL，后续维护成本会不断上升。
- **CI 只执行测试不执行门禁。** 报告覆盖率但允许低于底线合入，门禁没有实际约束力。
- **为了通过测试而删除有价值的断言。** 应该修复代码或明确更新契约，不能把测试改得更宽松。

## 记忆口诀

```text
单元测逻辑，集成测协作，API 测契约
不 mock 数据库，真实约束才可信
覆盖率是信号，不是质量本身
每次提交跑 CI，失败就不能合入
数据、依赖、配置、顺序都要隔离
```
