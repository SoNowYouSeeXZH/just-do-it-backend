# 11 日志与可观测性

> 对应迭代 6 · 已完成

## 一句话总结

日志回答“系统发生了什么”，指标回答“系统运行得怎么样”，追踪回答“一次请求经过了哪些模块”。企业后端至少要让每个请求有可关联的 `request_id`，记录方法、路径、状态码和耗时；慢请求要升级告警，错误响应不能泄露堆栈但必须能通过 request_id 找到日志。

## 核心概念

### Logging / Metrics / Tracing

```text
日志 Logging
  请求是什么、发生了什么错误、处理了多久

指标 Metrics
  请求量、错误率、P95/P99 延迟、数据库连接数

追踪 Tracing
  一次请求从网关到 API、Service、数据库、上游服务经过了什么
```

基础方案先实现日志基础设施和请求级关联；Metrics/Tracing 需要后续接入 Prometheus/OpenTelemetry 等系统，不能只靠打印日志假装完成。

### request_id

一个请求从客户端进入服务，到数据库或上游服务，可能产生多条日志。`request_id` 是这几条日志的共同索引：

```text
请求开始 request_id=abc123
数据库查询 request_id=abc123
上游调用 request_id=abc123
请求结束 request_id=abc123 status=200 duration_ms=42
```

用户拿到错误时，只需提供这个 ID，开发者就能搜索对应日志，而不是根据时间和文案猜是哪一次请求。

项目允许网关传入合法的 `X-Request-ID`；不合法或缺失时服务端重新生成。因为 request_id 会进入日志，不能原样相信客户端输入，当前只允许字母、数字、`.`、`_`、`-`，最多 128 个字符。

### 慢请求

平均耗时会掩盖尾部问题。一个接口平均 30ms，但 1% 请求耗时 3s，用户仍会明显感到卡顿。因此生产环境通常关注 P95/P99；基础方案先实现固定阈值：超过 `slow_request_ms` 就从 INFO 升级为 WARNING。

阈值通过环境变量配置：

```text
SLOW_REQUEST_MS=500
```

不同环境可能使用不同阈值，代码不需要修改。

### 健康检查

健康检查不是“进程还活着”这么简单，而是要区分：

```text
liveness  进程是否还能响应
readiness 关键依赖是否就绪，能否接收流量
```

当前 `/api/health` 执行 `SELECT 1` 探测数据库，返回：

```json
{
  "status": "ok",
  "database": "ok"
}
```

如果数据库不可用，健康检查应失败，让容器编排或负载均衡停止向这个实例发送流量。生产系统通常会把 liveness 和 readiness 拆成两个接口，避免数据库短暂故障导致进程被反复重启；基础方案先保持一个简单接口。

### 用户信息和日志脱敏

日志不是数据库，权限和保留周期通常更宽，不能把密码、JWT、API Key、身份证等敏感信息打进去。当前未知异常只把原始堆栈留在服务端日志，对外响应只返回通用文案和 request_id。

## 面试高频问答

**Q：日志、指标、追踪有什么区别？**

日志是离散事件，回答“发生了什么”；指标是随时间聚合的数值，回答“系统整体运行得怎么样”；追踪把一次请求跨服务的调用链串起来，回答“这一次请求慢在哪里”。排查问题通常先看指标发现异常，再用 request_id 查日志和追踪定位原因。

**Q：为什么需要 request_id？**

一次请求会产生多条日志，甚至跨多个服务。没有 request_id，只能依靠时间、路径、用户猜测日志属于哪次请求，并发高时很容易串错。把 request_id 同时写入响应和日志，用户报错时提供 ID，开发者就能精确检索完整链路。

**Q：为什么不能把异常堆栈直接返回给前端？**

堆栈可能泄露文件路径、依赖版本、SQL、表名和内部地址，为攻击者提供系统地图。正确做法是服务端日志记录完整堆栈（含 request_id），对外只返回通用错误文案和关联 ID。

**Q：健康检查只返回 200 就够了吗？**

不够。进程能响应不代表数据库、Redis、消息队列等关键依赖可用。readiness 检查应探测实际关键依赖，否则负载均衡可能把流量继续发给一个无法完成请求的实例。但探测也不能过重，健康接口只执行最小探针，例如数据库 `SELECT 1`。

**Q：为什么慢请求要记录 WARNING？**

慢请求不一定是错误，但它会影响用户体验并可能预示数据库慢查询、上游超时或资源耗尽。使用 WARNING 能让日志告警系统单独发现它。固定阈值是起点，生产上还要配合 P95/P99 等指标分析尾延迟。

**Q：客户端传来的 request_id 能直接写日志吗？**

不能完全信任。它会进入日志，如果允许换行或特殊控制字符，攻击者可能伪造日志内容；过长字符串还会污染日志系统。应限制字符集和长度，不合法时服务端重新生成。跨服务追踪需要透传时，也必须先校验。

## 易错点

- **只打“发生错误”日志，不记录请求上下文。** 没有路径、状态码、request_id，日志很难定位。
- **把 JWT、密码、API Key 写进日志。** 日志也需要脱敏和权限控制。
- **把堆栈返回给前端。** 堆栈留在服务端日志，对外只给通用文案和 request_id。
- **无条件透传客户端 request_id。** 可能造成日志注入或日志污染，必须校验。
- **只看平均耗时。** P95/P99 尾延迟更能反映真实用户体验。
- **健康接口做重查询。** 健康探针会被频繁调用，只做最小检查。
- **用一个健康接口解决所有问题。** liveness 和 readiness 语义不同，规模增大后应拆分。
- **日志等级滥用 ERROR。** 用户密码输错等预期业务失败不应淹没真正故障。
- **只在本地配置日志阈值。** 生产配置应通过环境变量管理，代码在不同环境保持一致。

## 记忆口诀

```text
日志看事件，指标看整体，追踪看链路
一个请求一个 request_id
错误堆栈留日志，响应只给安全提示
慢请求看尾延迟，不只看平均值
健康检查探测依赖，不只是返回 200
```
