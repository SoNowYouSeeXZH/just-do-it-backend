# 14 Redis 缓存与 Cache-Aside 模式

> 对应迭代 8 · 缓存部分已完成

## 一句话总结

缓存的难点从来不是"把结果存起来"，而是**什么时候失效、失效失败怎么办、缓存和数据库不一致怎么办**。工程上的核心判断有三条：缓存必须 fail open（Redis 挂了退化为查库，不能变成新的单点故障）；写操作必须"先更新数据库再删缓存"（顺序反了会把旧值长期写回缓存）；不是所有读接口都该缓存（随机抽题缓存了就不随机了）。

## 核心概念

### 三种缓存模式

```text
Cache-Aside（旁路缓存）—— 本项目采用
  应用主动读缓存 → 未命中查库 → 回写缓存
  应用完全掌控读写与失效时机，最常见、最可控

Read/Write Through（穿透读写）
  应用只跟缓存打交道，缓存自己负责同步数据库
  实现复杂，通常由缓存中间件提供

Write Behind（回写）
  先写缓存，异步刷库
  吞吐最高，但进程崩溃会丢数据
```

"旁路"的含义是缓存不在数据库前面强制拦截，而是放在旁边由应用主动查。

### fail open：缓存不能变成新的单点故障

这是最容易写错、代价最大的一条。

```text
错误写法
  Redis 抛异常 → 异常向上抛 → 接口 500
  结果：本来只想让系统更快，反而多了一个单点故障

正确写法
  Redis 抛异常 → 记日志 → 当作"未命中" → 查数据库 → 正常返回
  结果：Redis 挂了只是变慢，不影响可用性
```

本项目 `app/core/cache.py` 里所有 Redis 操作都包在 `try/except redis.RedisError` 里，出错返回 `None`（等于未命中）。`get_client()` 在未启用或连接失败时返回 `None` 而不是抛异常，让调用方用最自然的方式降级。

有个实现细节：降级时不能每个请求都打一条 ERROR 日志，否则 Redis 挂掉的同时日志系统也被打爆。用一个 `_degraded` 标志，只在状态从"正常"翻转到"降级"的那一次记录（`cache.py:50`）。

### 缓存穿透 / 击穿 / 雪崩

三个词经常被混用，但它们是完全不同的问题：

```text
穿透（Penetration）—— 查不存在的数据
  用随机 id 刷接口，缓存永远不命中，请求全打到数据库
  这是可被主动利用的攻击面
  解法：把"查不到"也缓存起来（短 TTL）；或用布隆过滤器

击穿（Breakdown）—— 单个热点 key 过期瞬间
  某个高频 key 刚过期，大量并发同时回源查库
  解法：互斥锁 / single flight（只让一个请求回源）；或热点 key 不过期

雪崩（Avalanche）—— 大批 key 同时过期
  一批 key 同时写入、TTL 相同 → 同一秒集体失效 → 数据库瞬时压力尖峰
  解法：TTL 加随机抖动；多级缓存
```

本项目做了穿透和雪崩的防护，**击穿没做**——它需要分布式锁或 single flight，对当前量级是过度设计；真需要时应该只给少数热点 key 加，而不是让所有查询都付锁的代价。这个取舍在 `cache.py` 的 `cache_aside` 文档里写明了，是有意的空白而不是遗漏。

### 防穿透：哨兵值区分"没缓存"和"缓存了空"

难点在于"空"的表达。如果直接存空字符串或 `"null"`，就无法和"业务数据本身是 null"区分。

本项目用一个业务上不可能出现的字符串当哨兵：

```python
_NULL_SENTINEL = "__cache_null__"     # cache.py:44

# 读出来时翻译成一个标记类
if raw == _NULL_SENTINEL:
    return CachedNull                  # cache.py:177
```

判断用 `is CachedNull`（类对象身份比较），不会和任何业务值相等，也不需要额外分配对象。

空值的 TTL 必须**明显短于**正常数据（本项目 30s vs 300s）。它只是挡穿透的临时挡板，不是真数据——如果和正常数据一样存 5 分钟，那么新建一个资源后，之前访问过的人要等 5 分钟才能看到。

### 防雪崩：TTL 抖动

```python
def _ttl_with_jitter(base: int) -> int:   # cache.py:79
    jitter = int(base * 0.1)
    return base + random.randint(-jitter, jitter) if jitter else base
```

假设首页一次加载写入 50 个 key、TTL 都是 300 秒，那么 300 秒后这 50 个 key 会在同一瞬间失效。抖动把它们摊到 270~330 秒之间。成本几乎为零，收益是削掉一个周期性的压力尖峰。

### 更新顺序：先写库，再删缓存

这是 Cache-Aside 里最容易出错的一环。

```text
正确：先 commit 数据库 → 再删缓存
  最坏情况是删缓存失败，脏数据活到 TTL 过期（有界）

错误：先删缓存 → 再写数据库
  删完缓存、库还没写完时，另一个请求来读，
  会把旧值重新加载进缓存 → 这个旧值要等整个 TTL 才过期
  表现：数据库已经是新的，缓存却一直是旧的（无界）
```

### 为什么是删除而不是更新

```text
删除（本项目采用）
  幂等，不用考虑并发写的先后顺序
  下一次读请求自然回填

更新
  需要知道新值的完整形状
  两个并发写可能以错误顺序落到缓存（写 A → 写 B → 缓存 B → 缓存 A）
```

本项目题库写入影响的是「职业列表的题目数」和「单个职业的题目数」两处**派生数据**，重算不如直接删掉。

还有一个细节：只在**真正写入了数据**时才失效（`question_bank.py:237` 的 `if created:`）。全部跳过或失败时数据没变，清缓存是白付一次回源成本。

### 按前缀失效要用 SCAN，不能用 KEYS

```text
KEYS pattern
  一次遍历整个 keyspace 并阻塞 Redis（它是单线程的）
  线上几十万 key 时足以造成一次可观测的抖动

SCAN cursor MATCH pattern COUNT n
  游标式分批扫描，不长时间占住服务
```

本项目用 `client.scan_iter(match=f"{prefix}*", count=100)`（`cache.py:169`），`scan_iter` 内部自动管理游标翻页。

用前缀而不是逐个删 key，是因为一次写入会影响多类派生缓存（列表题目数、详情题目数、题干列表），逐个删容易漏。

### 缓存该放哪一层

本项目放在 **Service** 层，不是 Repository：

```text
放 Service
  缓存粒度是"一次业务查询的结果"（职业 + 题目数拼装后的 DTO）
  命中时省掉的是整个业务流程，不只是一次 SQL

放 Repository
  只能缓存半成品，每次还要重新拼装
  而且 Repository 的职责是"如实读写数据库"，加缓存让它不再"如实"
```

### 序列化用 JSON，不用 pickle

```text
pickle
  反序列化可执行任意代码 → 缓存被写脏就是 RCE
  Python 专用，其他服务无法消费

JSON
  安全，能直接用 redis-cli 看，跨语言
```

代价是不能直接存 Pydantic 对象，要先 `model_dump()` 成 dict，读回来再 `model_validate()`。多一步转换，换来安全和可观测。

### 不是所有读接口都该缓存

判断标准是"**同样的输入是否应该得到同样的输出**"，而不是"这个接口是不是读接口"。

本项目 `sample_questions`（随机抽题）故意不缓存——它的语义就是每次返回不同的题，缓存会让随机性失效，用户重复进入同一职业会一直看到同一批题。

但它复用了带缓存的 `get_job` 做存在性校验（`job.py` 里 `get_job(session, job_id)`），所以恶意刷不存在的 id 也不会每次打到数据库。这是一个"部分缓存"的例子：把可缓存的那一半拆出来。

### 健康检查要区分必需依赖和可选依赖

```text
数据库不可用 → 探测抛异常 → 500 → 负载均衡停止发流量
缓存不可用   → 标记 degraded → 仍然 200
```

把缓存算成"不健康"会导致实例被误摘，反而放大故障。但也不能完全不报，所以本项目用三个状态：`ok` / `disabled`（有意关闭）/ `degraded`（连不上，需要有人看一眼）。见 `app/services/health.py:25`。

注意 `_cache_status()` 里刻意 catch 了宽异常——健康检查本身不能因为探测失败而抛错，否则缓存故障会连带把整个健康检查打成 500，数据库正常也被误判。

### Redis 部署要点

```text
不映射公网端口
  无密码的 Redis 暴露到公网是经典入侵入口
  （可以写 crontab、传 SSH 公钥）

必须设 maxmemory + 淘汰策略
  allkeys-lru：内存到上限时淘汰最久未使用的 key
  不设的话 Redis 会一直吃内存直到被 OOM kill

超时必须设小值
  缓存是为了更快，Redis 卡住时若无限等待，
  加缓存反而比不加更慢（本项目设 0.5s）

depends_on 用 service_started 而不是 service_healthy
  缓存是 fail-open 的，Redis 没就绪时应用会自动降级，
  不该因此阻塞启动
```

## 面试高频问答

**Q：缓存穿透、击穿、雪崩分别是什么，怎么解决？**

穿透是查不存在的数据，缓存永不命中，请求全打到数据库，可被主动利用来攻击；解法是缓存空结果（短 TTL）或布隆过滤器。击穿是单个热点 key 过期瞬间大量并发同时回源；解法是互斥锁或 single flight，让一个请求回源、其余等待。雪崩是大批 key 同时过期造成瞬时压力尖峰；解法是 TTL 加随机抖动。三者的区别在于"数据不存在" vs "单 key 过期" vs "批量 key 同时过期"。

**Q：更新数据时，应该先删缓存还是先更新数据库？**

先更新数据库，再删缓存。反过来的问题是：删完缓存、数据库还没写完时，另一个请求来读会把旧值重新加载进缓存，而这个旧值要等整个 TTL 才过期——数据库已经是新的，缓存却长期是旧的。先写库再删缓存的最坏情况只是删除失败导致脏数据活到 TTL，影响有界。更严格的场景可以用延迟双删或订阅 binlog 异步失效。

**Q：为什么失效时是删除缓存而不是更新缓存？**

删除是幂等的，不需要考虑并发顺序。更新缓存的话，两个并发写可能以错误顺序落到缓存上（写 A、写 B、缓存 B、缓存 A，最终缓存里是 A），造成缓存与数据库不一致。另外更新需要知道新值的完整形状，对派生数据（比如聚合出的计数）意味着要重算一遍，不如删掉让下次读自然回填。

**Q：Redis 挂了你的接口会怎样？**

会退化成直接查数据库，接口仍然可用，只是变慢。这叫 fail open。缓存是加速手段，不该变成新的单点故障——很多线上事故正是"Redis 抖动导致整站不可用"，因为代码把缓存当成了强依赖。具体做法是所有 Redis 操作包在 try/except 里，异常时当作未命中继续走数据库。同时健康检查要把缓存标记为 degraded 而不是让实例整体不健康，否则实例会被负载均衡误摘，反而放大故障。

**Q：怎么缓存"查不到"这个结果？直接存 null 有什么问题？**

直接存 null 或空字符串无法区分"这个 key 没被缓存过"和"缓存里明确记着数据库也没有"。需要一个业务上不可能出现的哨兵值（本项目用 `__cache_null__`），读出来时翻译成一个专门的标记。空值的 TTL 要明显短于正常数据，因为它不是真数据只是挡板——否则新建资源后，之前访问过的用户要等一个完整 TTL 才能看到。

**Q：按前缀批量删除缓存，为什么不能用 KEYS？**

Redis 是单线程的，`KEYS` 会一次遍历整个 keyspace 并在此期间阻塞所有其他命令，线上几十万 key 时足以造成可观测的服务抖动。应该用 `SCAN`，它是游标式分批扫描，每次只返回一小批，不会长时间占住服务。redis-py 的 `scan_iter` 封装了游标管理。

**Q：缓存应该放在哪一层？**

放业务层（Service）。缓存的合理粒度是"一次业务查询的结果"，命中时省掉的是整个业务流程；放数据访问层只能缓存半成品 SQL 结果，每次还要重新拼装。另外 Repository 的职责是如实读写数据库，加缓存会让它不再"如实"，也会让数据层测试变得难写。

**Q：所有读接口都应该加缓存吗？**

不是。判断标准是"同样的输入是否应该得到同样的输出"。本项目的随机抽题接口就不能缓存——它的语义是每次返回不同的题，缓存会让随机性失效。但可以把接口里可缓存的部分拆出来：抽题前的"职业是否存在"校验走缓存，这样恶意刷不存在的 id 也不会打到数据库。此外强一致性要求高的数据（余额、库存）也要谨慎。

**Q：缓存用 JSON 还是 pickle 序列化？**

JSON。pickle 反序列化可以执行任意代码，一旦有人能写 Redis 就等于远程代码执行；而且 pickle 是 Python 专用的，其他服务无法消费缓存，也无法用 redis-cli 直接查看排查。代价是不能直接存对象，要先转成 dict，多一步转换换来安全和可观测性。

**Q：Redis 部署时有哪些必须做的配置？**

不映射公网端口（无密码 Redis 暴露公网可被写 crontab、传 SSH 公钥，是经典入侵入口），即使内网也建议配 requirepass；必须设 `maxmemory` 和淘汰策略（如 `allkeys-lru`），否则会一直吃内存到被 OOM kill；连接和读写超时必须设小值，否则 Redis 卡住时加了缓存反而比不加更慢。

## 测试方法论

这一轮测试有两处值得记住的做法。

**用 fakeredis 而不是 mock。** mock 只能断言"调用了 `redis.set`"，无法验证"写进去的值能被正确读回来"、"TTL 到了会过期"、"SCAN 能匹配到前缀"——而这些才是缓存逻辑的关键。fakeredis 实现了真实的 Redis 语义，测的是行为而不是调用痕迹。

**用计数器验证"真的没查库"。** 判断缓存是否命中，不去检查 `redis.get` 被调用过，而是给 Repository 函数套一个计数器，断言第二次请求时计数没有增加。这更贴近我们真正关心的事情：省掉了数据库查询。

```python
calls = {"n": 0}
original = job_repo.list_jobs
def counted(*args, **kwargs):
    calls["n"] += 1
    return original(*args, **kwargs)
monkeypatch.setattr(job_repo, "list_jobs", counted)

client.get("/api/jobs")
client.get("/api/jobs")
assert calls["n"] == 1     # 第二次命中缓存
```

另外做了一次**反向验证**：临时把 `question_bank.py` 里的 `cache.delete_prefix` 注释掉，确认 `test_write_invalidates_job_cache` 确实失败，然后还原。这一步能证明测试真的在守护那段逻辑，而不是恰好通过——"测试通过"和"测试有效"是两件事。

## 易错点

- **把缓存当强依赖。** Redis 挂了整站 500。缓存必须 fail open。
- **先删缓存再更新数据库。** 会把旧值重新加载进缓存，且要等整个 TTL 才自愈。
- **只加缓存不写失效。** 表现是"数据库改了但接口一直返回旧值"，极易误判成写入失败。
- **失效时更新缓存而不是删除。** 并发写可能以错误顺序落到缓存。
- **不缓存空结果。** 留下穿透攻击面，随机 id 刷接口即可绕过缓存。
- **空值 TTL 和正常数据一样长。** 新建资源后要等一个完整 TTL 才可见。
- **一批 key 用相同 TTL。** 集体过期造成周期性压力尖峰。
- **缓存不设 TTL。** 一旦失效逻辑有遗漏，这个 key 会永久错下去。TTL 是最后兜底。
- **用 KEYS 批量删。** 阻塞单线程的 Redis，线上大 keyspace 时造成服务抖动。
- **给随机接口加缓存。** 随机性失效，用户反复看到同一批内容。
- **缓存放 Repository 层。** 只能缓存半成品，且让数据层不再"如实读写"。
- **用 pickle 序列化。** 缓存被写脏等于 RCE，且无法跨语言、无法用 redis-cli 排查。
- **Redis 不设 maxmemory。** 一直吃内存直到被 OOM kill。
- **Redis 无密码且映射公网端口。** 经典入侵入口，可被写 crontab、传公钥。
- **Redis 超时设太大或不设。** Redis 卡住时加了缓存比不加更慢。
- **缓存故障让健康检查失败。** 实例被负载均衡误摘，放大故障。
- **测试里 mock 掉整个缓存模块。** 只验证了调用痕迹，没验证缓存行为。
- **测试通过就认为测试有效。** 应当反向验证：破坏被测逻辑，确认测试会失败。
- **缓存里放了比接口更多的字段。** 题干接口若缓存完整题目对象，等于把答案也存进了 Redis，削弱了既有安全约束。
