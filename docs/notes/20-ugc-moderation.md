# 20 UGC 内容审核：先审后发、敏感词与审核队列

## 一句话总结

UGC 系统的审核不是"加一个敏感词表"，而是**一条状态流**：内容进来先定状态（`pending` / `published`），公开查询只认 `published`，可疑内容由规则引擎降级进人工队列，管理端用独立鉴权改状态——规则只是入口，状态机才是骨架。

## 核心概念

**先审后发 vs 先发后审。** 先审后发（新内容默认 `pending`）合规风险最低，但内容出现有延迟，冷启动社区会显得没人说话；先发后审（默认 `published`，事后巡检）体验好，但违规内容有暴露窗口。现实做法是**混合**：默认先发后审，命中规则的降级为先审后发。本项目用 `community_auto_publish` 控制默认策略，敏感词命中则无条件覆盖为 `pending`。

**未审核内容的可见性是安全约束，不是查询条件。** 公开列表的仓储函数 `list_published()` 把 `status == published` 写死在 SQL 里，管理端另走 `list_by_status()`。不合并成一个带 `status` 参数的函数——传参决定的约束，传错一次就是数据泄露。

**未发布 = 不存在。** 公开的单帖接口对 `pending` / `rejected` 返回 404 而不是 403。403 等于告诉探测者"这个 id 真实存在、只是没过审"，配合遍历 id 就能统计出平台在审什么内容。管理端接口相反，需要真实的 404 才能排查。

**规则引擎的定位。** 敏感词是成本近乎为零的第一道闸，能挡最直接的一批；语义变形、谐音、图片文字它一律挡不住。承认这个边界，才不会把它当成"审核已完成"。

## 面试高频问答

**问：敏感词过滤怎么防绕过？**
最基础的三种绕过都出在"字面比较"上：大小写变形、插入空格标点、全角半角。所以匹配前要先归一化——转小写、剔除所有非字母数字汉字的字符，再做包含判断。这样 `外 挂`、`S B`、`v.p.n` 都会被还原。再往上是同音字、拼音首字母、字形相近字、把文字画进图片，这些字面匹配挡不住，要上语义模型或第三方审核服务，规则引擎只负责便宜地挡住第一层。

**问：命中敏感词应该直接拒绝还是进人工复核？**
看误杀代价。词表是粗粒度的，"代练"可能出现在"举报代练"这种正常语境里，直接拒绝会伤到正常用户，而且用户不知道哪个词被拦、只能反复试。所以帖子命中后降级为 `pending` 进人工队列——延迟可见但不误杀。评论我做了不同选择：评论表没有审核状态列，一期不为它单独建队列，且评论短、改一句重发成本极低，所以直接拒绝。**同一套规则在不同内容体裁上可以有不同处置**，这是产品判断而不是技术判断。

**问：拒绝时能告诉用户命中了哪个词吗？**
不能。每次回显都在泄露词表的一个样本，攻击者可以二分探测出完整词表，然后精准绕过。所以错误响应只说"包含不允许发布的内容"。同理，审核日志只记 `post_id` + 命中词，不抄用户原文——日志的访问面比数据库宽得多，把敏感内容抄进日志等于又扩散一层。

**问：管理端接口为什么不用用户 JWT，而用 API Key？**
调用方不是"某个登录用户"，而是运营端或机器。用 JWT 就得引入角色/权限模型（`is_admin` 列、角色表、权限校验依赖），一期没有这个必要。API Key 的关键点是**比较必须用常量时间**（`secrets.compare_digest`）：`!=` 会在第一个不匹配字符处提前返回，攻击者能从响应时间差异逐位猜出密钥。另外入站的管理 Key 和出站的大模型 Key 要分开管理，一个泄露不影响另一个。

**问：审核状态用枚举还是字符串？**
用 `VARCHAR` + 模块常量。审核状态是会增长的（将来可能加 `appealing`、`auto_rejected`），数据库 ENUM 加值要改表结构，PG 上还要处理类型变更；字符串列加状态零成本。代价是数据库不再帮你兜非法值，所以校验要在入口做——我把审核接口的取值用 `Literal["published", "rejected"]` 限死在 DTO 上，非法状态在进业务层前就被 422 拦掉，业务层不用再写一遍校验。

**问：审核接口用 PUT 还是 PATCH？**
PATCH。语义上只改 `status` 一个字段，PUT 表示整体替换——用 PUT 就意味着客户端要提交完整资源，漏字段时服务端该不该清空？PATCH 避免了这个歧义。

## 实战方法

状态流与代码位置的对应：

```
发帖 ─┬─ 命中敏感词 ──────────────→ pending ─┐
      └─ 未命中 ─┬─ auto_publish=True → published │
                 └─ auto_publish=False → pending ─┤
                                                   ↓
                          GET /api/admin/posts?status=pending（审核队列）
                                                   ↓
                    PATCH /api/admin/posts/{id}/status {published|rejected}
```

- 规则引擎：`app/services/moderation.py` — 归一化 + 词表匹配，词表 = 内置默认 + `MODERATION_EXTRA_BANNED_WORDS` 环境追加
- 状态决策：`app/services/post.py::create_post` — 命中即覆盖 `auto_publish`
- 可见性边界：`app/repositories/post.py` — `list_published()` 与 `list_by_status()` 分开
- 管理端：`app/api/admin.py` — 复用 `require_admin_api_key`

默认词表放代码而不是数据库：它需要被 code review、需要有测试覆盖，改动频率也远低于业务数据。环境相关的追加词才走配置。

## 易错点

- **把"只看已发布"写成查询参数。** 一旦公开接口能传 `status`，就等于把审核形同虚设。约束要写死在数据访问层。
- **错误响应回显命中词。** 直觉上是"帮用户定位问题"，实际是泄露词表。
- **审核日志抄用户原文。** 日志系统的访问权限通常比数据库宽松得多。
- **只按 `created_at` 排序做分页。** 同一秒写入的多条记录顺序不稳定，翻页会重复或漏掉。要加主键作为第二排序键。这个坑在审核队列里尤其致命——漏掉的那条就是没人审的违规内容。
- **列表接口逐条查作者名。** 20 条帖子变 21 次查询（N+1）。作者名要在列表查询里 JOIN 出来。
- **以为敏感词过滤等于合规。** 它只是第一道闸，且是最容易被绕过的一道。真实上线还需要举报入口、人工审核 SLA、留存记录。
